> [!IMPORTANT]
> **重要考點**
>
> - IHE 的核心目標：==互操作性 Interoperability==。
> - **Actor＝資訊系統或醫療設備所承擔的功能角色；Transaction＝角色之間的資訊互動**。不要把交易當成醫護人員。
> - 互操作性由低到高：==基礎 → 結構 → 語意==；最高是語意。
> - **跨機構文件分享 → XDS.b；實機連測 → Connectathon；推動組織 → HIMSS＋RSNA**。
> - IHE 選用既有標準、描述流程與角色交易、推動連測；不以自行開發系統販售給醫院為核心工作。

# 1. IHE 解決什麼問題？

兩套系統即使都宣稱使用 HL7 或 DICOM，仍可能在訊息選項、必要欄位、流程及收到資料後的行為上不同。IHE 從臨床使用情境出發，界定交換內容及相關行為，讓開發者與採購者有較明確的共同語言。

IHE 促進既有標準協調使用，例如 HL7、DICOM 及安全標準；它不是取代這些標準的另一套完整資料格式。

本章第一節記載 **1998 年由 HIMSS 與 RSNA 合作推動 IHE**。

# 2. 互操作性的層次

| 層次              | 核心問題                       | 例子                                           |
| ----------------- | ------------------------------ | ---------------------------------------------- |
| 基礎 Foundational | 收得到資料嗎？                 | 能傳送並接收檔案／訊息，不必然理解內容         |
| 結構 Structural   | 格式與欄位能正確解讀嗎？       | 交換訊息的結構、語法及欄位一致                 |
| 語意 Semantic     | 對內容的意思是否一致並可使用？ | 知道數值的檢驗項目、單位與意義，能正確納入照護 |

==能互相連線，不代表內容能正確使用；格式相同，也不保證語意一致==。

# 3. 領域、技術架構、整合規範、角色與交易

| 名詞             | 定義                               | 例子                                         |
| ---------------- | ---------------------------------- | -------------------------------------------- |
| 領域 Domain      | 臨床或作業範圍                     | Radiology、ITI、Pharmacy                     |
| 技術架構 TF      | 該領域技術規範的集合與文件架構     | ITI TF                                       |
| 整合規範 Profile | 描述特定情境如何協調系統及標準     | XDS.b、SWF                                   |
| 角色 Actor       | 產生、管理或處理資訊的一組功能責任 | Document Source、Document Consumer           |
| 交易 Transaction | 角色間按規格進行的資訊互動         | Registry Stored Query、Retrieve Document Set |

角色不是特定公司、單一人員或必定獨立的電腦。一個產品可以實作多個角色，同一角色也可出現在不同產品；交易在此也不是付款或資料庫 ACID 交易的意思。

## 3.1 發展與維護流程

**定義臨床需求 → 選用標準並寫成規範 → 廠商實作 → 測試互通及回饋。**

# 4. SWF：影像排程工作流程

## 4.1 主要角色與常見系統

| 角色                             | 工作                         | 常見對應                                     |
| -------------------------------- | ---------------------------- | -------------------------------------------- |
| ADT／Patient Registration        | 病人登錄、基本資料與更新     | 掛號／病人行政系統                           |
| Order Placer                     | 開立影像檢查醫令             | HIS／醫令系統                                |
| DSS／Order Filler                | 部門接單、排程與執行管理     | RIS；此處 DSS 指 Department System Scheduler |
| Performed Procedure Step Manager | 接收與管理已執行程序步驟狀態 | 可與 RIS／影像管理功能整合                   |
| Acquisition Modality             | 擷取影像                     | CT、MR 等造影設備                            |
| Image Manager／Archive           | 管理及儲存影像               | PACS 相關功能                                |
| Image Display                    | 查詢、取得與顯示影像         | 判讀／檢視工作站                             |

## 4.2 主要交易與流程

| 流程           | 本章交易例子                                   | 意義                               |
| -------------- | ---------------------------------------------- | ---------------------------------- |
| 病人登錄／更新 | Patient Registration、Patient Update           | 使醫令與影像指向正確病人           |
| 醫令管理       | Placer／Filler Order Management                | 開單端與部門端同步醫令狀態         |
| 排程           | Procedure Scheduled                            | 部門通知安排的程序                 |
| 設備工作清單   | Query Modality Worklist                        | 設備取得已安排工作與資料，減少重打 |
| 執行狀態       | Modality Procedure Step in Progress／Completed | 回報造影步驟進行或完成             |
| 儲存影像       | Modality Images Stored、Storage Commitment     | 傳送影像並處理儲存責任確認         |
| 查詢與取得     | Query Images、Retrieve Images                  | 找到並取得所需影像                 |

**病人登錄 → 開立醫令 → RIS 排程 → 設備取得工作清單 → 造影及狀態回報 → PACS 儲存 → 工作站查詢、取得與顯示。**

# 5. XDS.b：先查索引，再取文件

## 5.1 六個角色

| 角色                      | 中文記法     | 職責                                                 |
| ------------------------- | ------------ | ---------------------------------------------------- |
| Document Source           | 文件來源     | 產生並發布文件與相關中繼資料                         |
| Document Repository       | 文件儲存庫   | 接收、保存文件本體，向 Registry 註冊中繼資料，供取件 |
| Document Registry         | 文件登錄庫   | 管理中繼資料及文件位置，接受查詢                     |
| Document Consumer         | 文件使用端   | 先查文件資料，再向儲存庫或適當來源取件               |
| Patient Identity Source   | 病人識別來源 | 提供識別資料供 Registry 關聯病人與文件               |
| On-Demand Document Source | 隨需文件來源 | 登錄可隨需產生的文件條目，回應取件要求               |

本章另列 Integrated Document Source／Repository，表示角色可整合在一起。==Registry 管索引，Repository 存文件本體==，這是本章最重要的區分。

## 5.2 七項交易對照

| 交易                                | 代碼   | 方向／用途                                           |
| ----------------------------------- | ------ | ---------------------------------------------------- |
| Provide and Register Document Set-b | ITI-41 | Source → Repository，提交文件及中繼資料              |
| Register Document Set-b             | ITI-42 | Repository → Registry，註冊中繼資料                  |
| Registry Stored Query               | ITI-18 | Consumer → Registry，尋找符合條件的文件              |
| Retrieve Document Set               | ITI-43 | Consumer → Repository／隨需來源，取得文件            |
| Patient Identity Feed               | ITI-8  | Patient Identity Source → Registry，提供病人識別資料 |
| Patient Identity Feed HL7v3         | ITI-44 | 同上，採 HL7 v3 方式                                 |
| Register On-Demand Document Entry   | ITI-61 | 隨需來源 → Registry，登錄隨需文件條目                |

> [!TIP]
> **三個常考區分**
>
> - **PDQ 查基本資料，PIX 對照識別碼**；demographics 不是「統計報表」。
> - **XUA 傳達身分聲明，不直接等於已獲所有資料的存取權限**。
> - **CT 對時、ATNA 記錄及驗證、BPPC 記同意**，不能互相取代。

# 10. Connectathon、整合宣告與展示

## 10.1 實機連測如何進行？

1. 廠商依規範、角色及選項完成實作與事前測試。
2. 在受監督的環境，與其他實作交換資料並執行指定交易。
3. 檢查交換內容及必要行為是否符合規範。
4. 記錄測試結果，供公開查詢及後續改善。

## 10.2 三種資料不要混淆

| 項目                               | 性質                     | 能說明什麼                                         |
| ---------------------------------- | ------------------------ | -------------------------------------------------- |
| Integration Statement 整合宣告     | 廠商公布的產品能力聲明   | 特定產品／版本支援哪些規範、角色與選項             |
| Connectathon Result 連測結果       | 指定活動中的實作測試結果 | 哪些範圍曾通過該次測試                             |
| Interoperability Showcase 互通展示 | 以情境示範資訊協作       | 讓使用者理解情境與能力，仍需核對實際測試及產品版本 |

| ---------- | ---------------------------------------------- |

# 12. 考前易混淆表

| 比較                   | 記法                                                   |
| ---------------------- | ------------------------------------------------------ |
| 標準與 IHE 規範        | 標準提供交換等基礎能力；IHE 選擇並約束其在情境中的用法 |
| Actor 與產品           | Actor 是功能角色；產品可實作一個或多個角色             |
| Transaction 與金流     | 本章 transaction 是資訊互動，並不表示收款              |
| Registry 與 Repository | 查索引找 Registry；取文件找 Repository／適當來源       |
| SWF 與 XDS.b           | 前者整合影像作業；後者分享文件                         |
| XDS.b 與 XDS-MS        | 前者偏交換機制；後者偏醫療摘要內容                     |
| 同標準與可互通         | 仍需對齊版本、選項、內容、角色、流程與安全治理         |
| 宣告與連測             | 宣告是廠商聲明；連測是指定範圍的實作結果               |
