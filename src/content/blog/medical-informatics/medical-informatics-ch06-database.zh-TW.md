> [!IMPORTANT]
> **重要考點**
>
> - 最優先：==主鍵唯一且不可 NULL；外鍵參照被參照表的主鍵，允許空值時可 NULL==。
> - **個體完整性看主鍵；參照完整性看外鍵與被參照表的關係**。外鍵本身不必唯一。
> - **全部完成或全部撤回 → 原子性；中間結果不受其他交易干擾 → 隔離性**。
> - DBMS 優點有減少重複、一致性、保密安全、**多種**使用者介面；「單一介面」「維護成本低廉」是常見錯項。
> - **外部層＝景觀、概念層＝整體邏輯、內部層＝儲存結構與存取路徑**。

# 1. 資料庫、DBMS 與應用系統

| 概念             | 定義                                             | 醫療例子                   |
| ---------------- | ------------------------------------------------ | -------------------------- |
| **資料庫**       | 具邏輯關聯、可組織與查閱的資料集合               | 病人、掛號、醫囑及計價資料 |
| **DBMS**         | 管理資料定義、查詢、新增、刪除、更新及控制的軟體 | 接收查詢並管理資料存取     |
| **資料庫系統**   | 應用程式、DBMS 與資料庫共同解決特定問題          | 掛號及醫令應用             |
| **檔案系統／OS** | 管理較底層的檔案與儲存資源                       | 資料檔在儲存裝置的保存     |

- **後設資料**記錄資料的定義、結構及關係；**索引**協助存取資料，兩者用途不同。
- 查詢取得符合條件的資料；異動包含**新增（INSERT）、刪除（DELETE）、更新（UPDATE）**。

# 2. ANSI-SPARC 三層綱要

| 層級                  | 描述什麼                                         | 掛號情境                                   |
| --------------------- | ------------------------------------------------ | ------------------------------------------ |
| **外部層 External**   | 特定使用者需要看到的資料與景觀                   | 掛號人員看基本資料；批價人員看計價所需資料 |
| **概念層 Conceptual** | 整個資料庫的實體、關係與限制，不描述實際儲存細節 | 病人資料、醫師資料、掛號關係的整體模型     |
| **內部層 Internal**   | 實際儲存結構、檔案組織、存取路徑及索引等         | 資料檔配置、存取方式                       |

- 目的：**資料獨立性、多使用者景觀、隱藏不必要的細節**。

# 3. 交易與 ACID

- **交易（transaction）**是包含一個或多個資料庫操作的工作單位。

| 特性                 | 核心意義                               |
| -------------------- | -------------------------------------- |
| **A 原子性／單元性** | 一個交易內的操作全部成功，或失敗時撤回 |
| **C 一致性**         | 交易前後資料維持一致                   |
| **I 隔離性／孤立性** | 交易執行如同單獨執行，不受其他交易干擾 |
| **D 持久性／永久性** | 成功完成的交易結果永久保留             |

# 4. DBMS 的優缺點與分類

| 優點           | 意義                                 |
| -------------- | ------------------------------------ |
| 減少資料重複   | 透過整體設計與正規化降低冗餘及不一致 |
| 保密與安全控制 | 管理不同使用者的查閱、更新及刪除權限 |
| 加強一致性     | 透過限制與交易控制，協調資料異動     |
| 程式與資料獨立 | 減少程式直接依賴實體檔案結構         |
| 多種操作介面   | 支援表單、查詢及程式介面等不同需求   |

## 不同分類軸

| 分類依據 | 類別                                           |
| -------- | ---------------------------------------------- |
| 資料模型 | 關聯式、物件導向式、物件關聯式、階層式、網路式 |
| 使用者數 | 單一使用者、多使用者                           |
| 配置方式 | 集中式、分散式                                 |

| 資料模型       | 表達方式                     | 要記住的特性                   |
| -------------- | ---------------------------- | ------------------------------ |
| **關聯式**     | 表格、列、欄與鍵值           | 以多個資料表及關係組織資料     |
| **物件導向式** | 物件、狀態、行為、類別與方法 | 同時表達資料與操作             |
| **物件關聯式** | 關聯模型結合物件概念         | 在關聯基礎上擴充               |
| **階層式**     | 根與父子節點形成樹           | 典型父子為一對多；子只有一個父 |
| **網路式**     | 記錄與集合型態形成網路       | 可透過連結記錄表達多對多       |

- 本章的網路式集合型態有三要素：**名稱、owner（所有者）、member（隸屬者）**。

# 5. 關聯式資料表的基本概念

| 名詞                | 意義                                    |
| ------------------- | --------------------------------------- |
| Relation／Table     | 關聯／資料表                            |
| Column／Attribute   | 欄／屬性，如病歷號碼                    |
| Row／Record／Tuple  | 列／紀錄／值組，如某位病人的一筆資料    |
| Cell                | 列與欄的交點；在本章 1NF 的設計中為單值 |
| Domain              | 值域，欄位允許的值及限制                |
| Schema              | 綱要，定義欄位、結構及限制              |
| Instance／Extension | 實例／當下的資料內容                    |

- **綱要相對穩定，資料內容持續異動**。

# 6. 鍵值與完整性限制

| 名稱                     | 定義                               |
| ------------------------ | ---------------------------------- |
| **超級鍵 Superkey**      | 能唯一識別紀錄的屬性集合           |
| **候選鍵 Candidate key** | 可唯一識別紀錄，且不含多餘屬性的鍵 |
| **主鍵 Primary key**     | 從候選鍵選定的主要識別方式         |
| **複合鍵 Composite key** | 由多個欄位共同組成的鍵             |
| **外鍵 Foreign key**     | 參照其他資料表主鍵的欄位           |

- **個體完整性**：主鍵值不可為空，且必須唯一。
- **參照完整性**：外鍵有值時須能匹配被參照的鍵；若允許 NULL，才可空缺。

# 7. 三種異動異常

| 異常               | 本章情境                                         | 問題根源                     |
| ------------------ | ------------------------------------------------ | ---------------------------- |
| **新增異常**       | 新醫師尚無檢查報告，無法填入以檢查資料為鍵的大表 | 不同事實被迫綁在同一筆紀錄   |
| **刪除異常**       | 刪除病人的最後一筆報告，同時失去他的基本資料     | 刪除一種事實時誤失另一種事實 |
| **更新／修改異常** | 同一病人的電話有多筆，只更新其中一筆             | 重複保存同一事實造成不一致   |

# 8. 功能相依與正規化

## 8.1 先理解功能相依 FD

**X → Y** 表示：在資料模型規定的所有合法資料狀態中，==X 值相同時，Y 值必須相同==。

- **完全相依**：Y 需要整組 X 才能決定，X 的任何真子集都不足以決定 Y。
- **部分相依**：Y 只依賴複合候選鍵的一部分。
- **遞移相依**：例如「檢查單號 → 病歷號碼 → 病人姓名」。

## 8.2 各正規化形式比較

| 形式     | 核心條件                                     | 辨識方式                         |
| -------- | -------------------------------------------- | -------------------------------- |
| **1NF**  | 每個欄位在該模型中為單值，沒有重複群組       | 一格是否塞入多個項目？           |
| **2NF**  | 已達 1NF；非鍵屬性完全相依於鍵，沒有部分相依 | 是否只依賴複合鍵的一部分？       |
| **3NF**  | 已達 2NF；移除非鍵屬性的遞移相依             | 是否透過另一非鍵屬性而相依？     |
| **BCNF** | 資料表中的決定項都必須能唯一識別紀錄         | 每個決定項能否識別整筆？         |
| **4NF**  | 已達 BCNF；處理互相獨立的多值相依            | 是否混放兩組互相獨立的多值事實？ |
| **5NF**  | 進一步處理合併相依，分解後仍可還原           | 是否仍有須進一步分解的合併相依？ |

- 強度關係：**5NF ⇒ 4NF ⇒ BCNF ⇒ 3NF ⇒ 2NF ⇒ 1NF**。

## 8.3 1NF：把重複群組展開

若一筆檢查單的造影儀器欄位是 `{CT, X Ray}`，就把兩個項目分成兩列。

| 檢查單號 | 造影儀器 |
| -------- | -------- |
| R223456  | CT       |
| R223456  | X Ray    |

## 8.4 2NF：移除部分相依

原大表的鍵為 **（檢查單號，造影儀器）**，但：

```text
（檢查單號，造影儀器）→ 各項檢查及報告資料
檢查單號 → 病歷號碼、病人姓名、生日、性別、電話
```

後者只依賴複合鍵的一部分，因此拆成：

| 表               | 欄位概念                                                   | 鍵             |
| ---------------- | ---------------------------------------------------------- | -------------- |
| 檢查明細         | 檢查單號、儀器、診斷碼、檢查日期時間、報告、醫師及報告日期 | 檢查單號＋儀器 |
| 檢查單與病人資料 | 檢查單號、病歷號碼、姓名、生日、性別、電話                 | 檢查單號       |

==2NF 解決的是「只依賴鍵的一部分」，不會順便保證所有遞移相依都消失。==

## 8.5 3NF：移除不適當的遞移相依

本章的兩條重要鏈結：

```text
（檢查單號，儀器）→ 報告醫師代碼 → 醫師姓名
檢查單號 → 病歷號碼 → 病人姓名、生日、性別、電話
```

因此再拆成四個主題清楚的表：

| 表           | 主要欄位                             | 主要識別與連結                                    |
| ------------ | ------------------------------------ | ------------------------------------------------- |
| **病人**     | 病歷號碼、姓名、生日、性別、電話     | PK：病歷號碼                                      |
| **醫師**     | 醫師代碼、姓名                       | PK：醫師代碼                                      |
| **檢查單**   | 檢查單號、病歷號碼                   | PK：檢查單號；FK：病歷號碼                        |
| **檢查明細** | 檢查單號、儀器、報告、報告醫師代碼等 | 複合 PK：檢查單號＋儀器；相應 FK 連結檢查單與醫師 |

## 8.6 BCNF：決定項必須是超級鍵

本章額外假設：==每位報告醫師只負責一種造影儀器==。

```text
報告醫師代碼 → 造影儀器
```

- 醫師代碼能決定儀器，卻不能決定所有檢查紀錄，因此不是原表的超級鍵。
- 依本章再分成「**醫師－儀器**」與保留醫師代碼的「**檢查明細**」，避免在每筆檢查反覆保存相同的醫師－儀器對應。

## 8.7 4NF：拆開互相獨立的多值關係

多值相依的情境：一部儀器可以由多位醫師使用，也可由多位維護人員維護，而且兩組關係互相獨立。

- 若放在「儀器、醫師、維護人員」一表，2 位醫師與 2 位維護人員會產生 **2 × 2＝4 筆**組合。
- 拆成 **儀器－醫師**與**儀器－維護人員**兩表，分別保存兩種獨立的事實。

## 8.8 5NF：合併相依

- 本章僅介紹概念：檢查資料表能否進一步分解，並經合併還原。

# 9. 分解資料表時的兩項檢查

| 檢查                                   | 問的問題                                                     |
| -------------------------------------- | ------------------------------------------------------------ |
| **無損失合併 Lossless join**           | 拆表後能否正確還原原資料，不遺失，也不產生原本不存在的組合？ |
| **相依性保留 Dependency preservation** | 原有相依限制能否由分解後各表的限制維持？                     |

- **無損失**與**相依保留**是不同性質，不能混為一談。
