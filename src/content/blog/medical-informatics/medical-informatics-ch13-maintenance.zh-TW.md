> [!IMPORTANT]
> **重要考點**
>
> - 本章最值得先背的只有一張表：==矯正、適應、完善、預防==。
> - **錯誤修正 → 矯正；外在環境改變 → 適應；新增／改良功能 → 完善；改善未來可靠度 → 預防**。
> - 常見錯項是把「新增功能」配到矯正或預防，以及把保固說成「不包含矯正性維護」。
> - 維護期間與範圍由契約規範；一年是本章的常見契約情境，不能據此改變四類維護的定義。

# 1. 系統正式上線

## 1.1 四個成功關鍵

| 關鍵                     | 作法                                       |
| ------------------------ | ------------------------------------------ |
| 準備 Prepare             | 確認設備、表單、資料、版本、訓練與支援人力 |
| 溝通 Communicate         | 明確窗口、公告與問題回報，減少互相推諉     |
| 危機處理 Risk management | 預先規劃故障應變、分工及恢復作業           |
| 鼓勵 Encourage           | 理解臨床工作壓力，現場協助使用者建立信心   |

## 1.2 正式上線的四項注意事項

1. **決定上線日期**：考慮營運、財務與申報週期，完成資料交換及申報測試。本章以「每月一日、零時」為常見安排，不能當成所有醫院強制規定。
2. **區分上線階段**：本章建議門診、住院、管理系統分階段上線，避免同時需要大量支援，超出人力負荷。
3. **管理舊資料及基本資料**：排除測試資料、將舊系統正式資料轉入並核對；確認電腦、印表機、紙張及表單；提供緊急聯絡方式；維持各單位版本正確一致。
4. **建立問題處理程序**：使用者填寫顧客意見處理單，品質控制小組彙整分類，交責任單位處理並追蹤。

## 1.3 問題單與統計

| 類別     | 應記錄內容                                             |
| -------- | ------------------------------------------------------ |
| 提出資訊 | 日期、時間、單位、聯絡人及方式                         |
| 問題內容 | 資料異常、應用軟體、硬體、線路、業務或其他；描述與附件 |
| 處理資訊 | 受理人、處理人、受理及處理時間、解決方式               |
| 確認資訊 | 審核、使用者簽收或確認                                 |

品質控制小組按月統計：**已處理、進行中、待處理、駁回**，比較各月份狀況。問題處理單範例中的「三個工作天內處理」是範例中的服務約定；緊急問題應依影響與契約另訂優先級和時限。

## 1.4 上線常見困難

- 使用者多、各科需求不同，需整合共通流程並處理必要差異。
- 醫護人員臨床負荷高，練習時間有限，需要現場支援與訓練安排。
- 工程與醫療雙方都應配合專案計畫、清楚回報問題，避免互相責備。

# 2. 系統維護的四種類型

| 類型              | 主要目的                       |
| ----------------- | ------------------------------ |
| 矯正性 Corrective | 修正已發現的錯誤               |
| 適應性 Adaptive   | 讓系統適應環境改變             |
| 完善性 Perfective | 增加或改善功能與效能           |
| 預防性 Preventive | 處理潛在問題，提升未來可維護性 |

記憶：**錯了修、環境變要適應、不夠好再完善、未出事先預防。** 分類仍須看變更的主要目的。

## 2.1 維護範圍由什麼決定？

以雙方契約及確認的需求規格為依據，明定期間、服務內容、優先順序與責任。本章提及一年維護期及擴充另約的情形，是本章案例，並非所有專案的固定期限與計價規則。

# 4. 品質控制與品質保證

## 4.1 六個品質面向

| 面向         | 管什麼？                             | 記憶例子                                                   |
| ------------ | ------------------------------------ | ---------------------------------------------------------- |
| **產品品質** | 採購的軟硬體，以及彼此搭配的整體效益 | 主機、網路、作業系統、資料庫的效能、成本、擴充及維護便利性 |
| **施工品質** | 安裝、架設及施工過程                 | 事前安排與公告；施工時減少干擾；完工後復原並整理環境       |
| **生產品質** | 專案開發產物與開發過程               | 系統、程式碼、文件及特定需求的設計成果                     |
| **保固品質** | 正常運作的後續維持與故障恢復         | 應變計畫、演練、處理效率與恢復能力                         |
| **人員品質** | 院方、資訊廠商及協力廠商的人員       | 專業、負責、誠懇溝通、技能與工作態度                       |
| **管理品質** | 管理階層的規劃、支持、控制與應變     | 明確規範、資源支持、進度與成果管理                         |

本章對管理原則的口訣為：**完整規劃、明確規範、全力支持、強力要求、全才學習、賞罰分明**。另提及具經驗顧問協助規劃、協調及監督，但是否聘請須看專案需求。

## 4.2 品質制度

| 名稱          | 本章用途                             |
| ------------- | ------------------------------------ |
| ISO 9000      | 品質管理與品質保證相關標準           |
| CMMI          | 能力成熟度模型整合，用來改善組織流程 |
| ISO/IEC 15504 | 軟體流程評鑑相關標準                 |

# 5. McCall 軟體品質模型

## 5.1 三面向、十一因素

| 面向                            | 品質因素                 | 問的是什麼？                     |
| ------------------------------- | ------------------------ | -------------------------------- |
| **產品操作 Product operation**  | 正確性 Correctness       | 是否符合規格與使用需求？         |
| 同上                            | 可靠性 Reliability       | 能否穩定完成預期工作？           |
| 同上                            | 效率性 Efficiency        | 時間、記憶體等資源使用是否合宜？ |
| 同上                            | 完整性／防護性 Integrity | 是否控制未授權存取？             |
| 同上                            | 易用性 Usability         | 學習與操作是否容易？             |
| **產品更改 Product revision**   | 可維護性 Maintainability | 是否容易找出並修正問題？         |
| 同上                            | 彈性／修改性 Flexibility | 是否容易修改以符合新需求？       |
| 同上                            | 可測試性 Testability     | 是否容易驗證功能與找出錯誤？     |
| **產品移轉 Product transition** | 可攜性 Portability       | 是否容易移到不同環境？           |
| 同上                            | 再利用性 Reusability     | 元件是否能用在其他應用？         |
| 同上                            | 互通性 Interoperability  | 能否與其他系統交換並使用資訊？   |
